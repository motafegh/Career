## 1. Purpose

Ali already pays for and deliberately uses capable AI systems as a core part of his engineering and learning model. The opportunity is not merely to “use more tokens” or keep an AI subscription busy.

The real question is:

> **Which useful parts of Ali's Career, learning, project support, research, market work, portfolio work, and re-entry preparation can AI advance with little or no live Ali attention, so focused attention is preserved for judgment, technical understanding, verification, diagnosis, meaningful modification, decisions, communication, and ownership?**

This plan investigates that question systematically and then adopts only workflows whose real value exceeds their attention/review cost.

The intended outcome is a small practical **AI leverage system around Ali's existing work**, not another large project, productivity bureaucracy, or technology collection exercise.

---

## 2. Career boundary

This is a Career-level investigation because it concerns Ali's personal attention, learning productivity, Career operating system, and use of AI across projects.

Career may:

- classify work by Ali-attention requirement;
- identify candidate delegable/review-later/low-energy workflows;
- define attention-ROI criteria;
- test workflows using legitimate current Career/project material;
- decide which workflows deserve repeatable Career-level use;
- recommend bounded project-local workflows to the relevant project when the workflow belongs there;
- decide whether a mature workflow deserves a Skill, automation, template, or no durable machinery at all.

Career must not:

- take ownership of UpgradePilot or another project's technical continuation;
- automate away Ali's required technical ownership;
- infer capability from AI-produced artifacts;
- create fake engineering work so an AI can stay busy;
- force new project architecture, source changes, tests, exercises, or tooling merely to enable background AI use.

Project-local technical workflows remain governed by their project repositories.

## 3. Core principle

Do **not** optimize for subscription utilization.

Optimize for:

> **Useful progress and future focused time saved per unit of Ali attention.**

A workflow is valuable when it creates one or more of:

- future focused-time savings;
- lower re-entry cost after breaks;
- higher-quality preparation before Ali starts focused work;
- reusable learning material;
- better filtering/compression of large information spaces;
- better review, challenge, or verification candidates;
- productive low-energy learning;
- legitimate portfolio/market/interview preparation;
- better continuity without replacing Ali's decisions or ownership.

A workflow is weak when it mainly creates:

- AI output volume;
- more files to review;
- duplicate summaries;
- low-value notifications;
- generic study material;
- fake work or fake evidence;
- maintenance overhead greater than the time saved;
- plausible-looking conclusions Ali cannot verify.

## 4. Attention classes

Every candidate workflow should first be classified into one of four modes.

### A. `FOCUS_REQUIRED`

Ali must participate materially because the responsibility carries important judgment, ownership, risk, or learning value.

Typical examples:

- consequential technical/product decisions;
- acceptance criteria and claim boundaries;
- architecture/responsibility decisions;
- causal debugging decisions;
- meaningful modification decisions;
- interpretation of ambiguous or conflicting evidence;
- final Career strategy/readiness/allocation decisions;
- final external claims;
- interviews and actual capability demonstration.

AI may assist heavily, but the responsibility must not be reduced to unattended AI output.

### B. `REVIEW_LATER`

AI can perform substantial work independently and Ali can inspect the result later before it becomes trusted/adopted.

Candidate examples:

- bounded research dossiers;
- independent audit/challenge passes;
- candidate test/evaluation cases;
- project orientation/change summaries;
- next-session preparation;
- portfolio/interview explanation drafts;
- market/job classification drafts;
- documentation cleanup proposals;
- synthesis/comparison of already-available evidence.

### C. `BACKGROUND_SAFE`

AI can produce a useful artifact with very low decision risk and no need for live Ali interaction; later inspection may be light or purpose-specific.

Candidate examples:

- learning-artifact authoring from an already-bounded responsibility;
- NotebookLM-ready learning source packages;
- fast-relearning summaries from an accepted learning artifact;
- glossary/index generation from verified material;
- formatting/organization work;
- stale-link/navigation detection;
- source collection for an already-defined research question.

This class must remain narrow. “AI can do it” is not enough; incorrect output must have bounded consequences.

### D. `LOW_ENERGY`

Ali remains involved, but the activity is intentionally usable when concentration is below focused-engineering level.

Candidate examples:

- listening to project-grounded audio/podcast learning;
- conversational recap;
- one-concept learning;
- a few retrieval questions;
- one bounded code-reading snippet;
- architecture/data-flow walkthrough;
- interview-story listening/rehearsal;
- reviewing a prepared orientation package without starting implementation.

Low-energy work is optional productive capacity, not a requirement to eliminate rest.

## 5. Attention-ROI model

Evaluate candidates using a qualitative scorecard rather than token count.

For each candidate estimate:

```text
BENEFIT
future focused time saved
+ learning value
+ Career value
+ project value
+ continuity/re-entry value
+ reuse frequency
+ quality improvement

COST / RISK
Ali setup attention
+ Ali review burden
+ verification difficulty
+ hallucination/error consequence
+ maintenance/context cost
+ duplication risk
+ ownership displacement risk
```

The strongest workflows should have:

- low setup burden;
- bounded output;
- clear evidence/source boundary;
- high reuse or meaningful one-time savings;
- low cost of detecting an AI error;
- no substitution for important Ali-owned responsibility.

Do not force a numeric formula unless real comparisons require one. Use `HIGH / MEDIUM / LOW` judgments with brief evidence first.

## 6. Candidate opportunity families to investigate

The audit must search broadly enough to avoid overfitting to the first idea, while remaining tied to Ali's real Career system.

### 6.1 Learning preparation and transformation

Investigate:

- UpgradePilot-style learning artifacts;
- fast-relearning versions;
- NotebookLM/podcast source packages;
- concept/term maps;
- test/proof explanations;
- changed-context/ownership questions;
- project-history-to-learning synthesis;
- audio-first variants for low-energy periods.

Use the existing UpgradePilot `upgradepilot-learning-artifact` Skill as one proven reference workflow, not as a Career-wide implementation owner.

### 6.2 Re-entry and next-session preparation

Investigate a “Future Ali” preparation workflow such as:

```text
current responsibility / current evidence
→ what changed
→ what matters now
→ important source/tests/owners
→ concepts to remember
→ proof/non-proof
→ likely re-entry questions
→ project-owned continuation link
```

The workflow must reduce restart cost without duplicating project live state into Career.

### 6.3 Background research/scouting

Investigate bounded AI research for:

- technical concepts encountered in real work;
- AI/agent engineering practices;
- tool/library comparisons;
- market/role changes;
- architecture alternatives;
- documentation/reference collection.

Research output must separate source evidence, synthesis, uncertainty, and recommendation.

### 6.4 Independent audit/challenge work

Investigate whether a second AI pass can usefully challenge:

- design assumptions;
- code/test reasoning;
- missing proof;
- overengineering;
- stale documentation;
- weak external claims;
- research conclusions.

The challenge agent should produce findings/candidates, not silently become the decision owner.

### 6.5 Test/evaluation candidate generation

Investigate AI generation of candidate:

- changed cases;
- edge/negative cases;
- adversarial cases;
- failure families;
- evaluation rubrics;
- interview practical prompts.

Ali/project owners decide which cases are meaningful and admitted.

### 6.6 Portfolio and interview preparation

Investigate background preparation of:

- 30-second / 2-minute / deep technical project explanations;
- responsibility stories;
- debugging stories;
- AI-assistance/ownership explanations;
- likely interviewer follow-ups;
- claim-safe project evidence extracts;
- mock interview question sets based on actual project responsibilities.

No generated narrative becomes a public claim without Career claim review when material.

### 6.7 Market/application support

After application activation, investigate:

- vacancy intake/classification;
- responsibility-bundle extraction;
- access-gate detection;
- repeated-gap detection;
- company/role research packs;
- interview preparation packs;
- feedback categorization.

Do not automate application decisions or rewrite Career strategy from one vacancy.

### 6.8 Career/project continuity and knowledge maintenance

Investigate bounded AI work such as:

- owner/link/staleness scans;
- completed-plan lifecycle checks;
- public-safe project summary refresh candidates;
- evidence-index preparation;
- “what changed since I last studied this?” packages.

Do not create continuous monitoring or maintenance ceremony without demonstrated value.

### 6.9 Personal low-energy learning

Investigate a menu of activities that can genuinely work when Ali is not ready for a focused engineering session:

- audio learning;
- conversational recap;
- five-question retrieval;
- one code-flow reading;
- one concept from current work;
- vocabulary/term recovery;
- project story rehearsal;
- reading/reviewing an AI-prepared pack.

The goal is to convert some otherwise-lost periods into optional useful exposure/retrieval, not to eliminate rest or turn every free moment into work.

### 6.10 Autonomous/supporting project work

JobHunter and Sentinel already contain AI-full-implementation work that can progress without becoming Ali capability evidence.

Investigate only whether there are Career-level support outputs worth requesting from such autonomous work—for example market intelligence or portfolio evidence preparation. Do not convert them into parallel flagship learning commitments.

Establish:

**Output:** baseline constraints in the progressive report.

### P1 — Inventory real recurring work and attention friction

Map actual recurring activities across:

- UpgradePilot learning/building;
- Career/E2/applications;
- JobHunter/Sentinel supporting work;
- technical research;
- learning/relearning;


**Output:** real-work inventory.

### P2 — Classify the opportunity space

Assign candidate tasks to:

```text
FOCUS_REQUIRED
REVIEW_LATER
BACKGROUND_SAFE
LOW_ENERGY
```

Reject candidates that would:

- automate Career/project decisions;
- manufacture capability evidence;
- create security/privacy risk;
- require more review than they save;
- create large new systems before value is proven.

**Output:** attention-class map.

---

### P3 — Generate and score workflow candidates

For each useful recurring friction, propose the smallest AI-assisted workflow.

Record:

- problem/friction;
- attention class;
- input/source boundary;
- AI action;
- output;
- Ali review/interaction requirement;
- failure/error risk;
- likely attention/time savings;
- reuse frequency;
- ownership boundary;
- tentative Attention-ROI (`HIGH / MEDIUM / LOW`).

**Output:** candidate workflow matrix.

---

### P4 — Prioritize a small pilot set

Select approximately **3–5** candidates that collectively test different leverage patterns.

Default candidates to pressure first, subject to P1–P3 evidence:

1. post-session/project learning package;
2. next-session/re-entry preparation pack;
3. low-energy audio/retrieval workflow;
4. bounded background research scout;
5. independent audit/challenge pass.

Do not pilot everything at once.

**Output:** pilot set + rejection/defer list.

---

### P5 — Run bounded real-world pilots

Use legitimate existing work rather than synthetic productivity demonstrations.

For each pilot:

1. define the exact real input/responsibility;
2. record how much Ali setup was required;
3. let AI perform the allowed work;
4. measure/reconstruct later review burden;
5. determine whether Ali actually used the result;
6. estimate focused-time/re-entry/learning benefit;
7. record material errors or trust problems;
8. determine whether the workflow strengthened or weakened ownership.

Evidence can be qualitative. Do not build a time-tracking bureaucracy.

**Output:** pilot evidence records in the progressive report.

---

### P6 — Design the low-energy operating menu

From successful pilots, define a very small **low-energy menu** that Ali can choose from without planning overhead.

Possible shape:

```text
5–10 minutes
→ one concept / 3–5 retrieval questions / prepared recap

15–30 minutes
→ audio episode / code-flow walkthrough / project story rehearsal

30–60 minutes when willing but not fully focused
→ review a prepared orientation/research/audit pack
```

This must remain optional and should include **rest / do nothing** as a valid outcome when work would be counterproductive.

**Output:** low-energy menu candidate.

---

### P7 — Decide persistence/automation level for each successful workflow

For each successful pilot choose the smallest appropriate form:

```text
AD HOC PROMPT
→ one-off or rare; no durable machinery

REUSABLE PROMPT / TEMPLATE
→ repeated but simple

PROJECT-LOCAL SKILL
→ repeated project-specific procedure with real routing/evidence needs

CAREER WORKFLOW / SKILL
→ repeated Career-level procedure with stable responsibility

AUTOMATION
→ recurring or conditional future delivery genuinely saves repeated checking

EXTERNAL TOOL PIPELINE
→ e.g. learning artifact → NotebookLM audio when another tool clearly adds value

REJECT / DEFER
→ insufficient attention ROI or too much risk/maintenance
```

Do not create a Skill merely because a good prompt exists.

**Output:** adoption matrix.

---

### P8 — Integrate with Career without creating a second bureaucracy

For adopted workflows decide where, if anywhere, durable ownership belongs.

Rules:

- live Career state remains in `CAREER_STATE.md` only;
- project technical workflow stays project-local;
- no new daily tracker by default;
- no quota for number of AI tasks/tokens;
- no requirement to run every workflow after every session;
- workflow use should be triggered by real friction/value.

Update canonical Career files only if a material durable decision actually changes.

**Output:** minimum integration set.

6. Which deserve durable Skills/templates/automation?

## 8. Initial hypotheses to test, not assume

### H1 — Re-entry preparation may have very high attention ROI

Because breaks create orientation cost, a well-bounded “Future Ali” pack may save more focused time than many traditional productivity automations.

### H2 — Learning transformation is already a validated opportunity family

The UpgradePilot learning-artifact → NotebookLM audio workflow likely deserves expansion, but only if the derived formats are actually consumed and help later project ownership.

### H3 — Independent AI challenge may improve engineering quality at low live-attention cost

A second AI can inspect assumptions/tests/design and prepare findings for later review, but only if the review burden stays bounded and the challenge output is not mistaken for proof.

### H4 — Research scouting can save substantial focused time

AI can perform source discovery/comparison/synthesis while Ali retains final interpretation and adoption decisions.

### H5 — Low-energy work should use retrieval/comprehension, not heavy decision-making

Audio, recaps, one-concept study, and bounded retrieval may convert some low-energy periods into useful reinforcement without putting consequential work into a poor-attention state.

### H6 — Market/application leverage becomes especially valuable after E2

Vacancy classification, company research, interview packs, and feedback coding may be strong review-later workflows once the application lane is active.

### H7 — Maximizing subscription usage directly would be harmful

A token/use quota would incentivize low-value tasks, excess artifacts, and false productivity. The useful metric is attention ROI and actual reuse.

## 9. Pilot acceptance criteria

A workflow is a strong adoption candidate when most of these are true:

- solves a real recurring friction;
- saves meaningful future Ali attention or increases useful low-energy capacity;
- output is bounded and inspectable;
- AI errors are reasonably detectable;
- review cost is clearly lower than doing the whole task manually;
- does not displace important judgment/technical ownership;
- can be reused without large setup;
- does not duplicate a canonical owner;
- produces something Ali actually uses;
- does not require another large system to maintain it.

Reject or narrow when:

- output is rarely used;
- verification is as expensive as doing the work;
- hallucination/error risk is high and difficult to detect;
- the workflow removes a responsibility Ali needs to learn/own;
- it creates more context/files/notifications than value;
- it encourages working when rest would be better;
- its main justification is “the subscription would otherwise go unused.”

## 10. Privacy, safety, and account boundary

Do not use this program to move confidential, private, credential-bearing, health, financial, or employer-sensitive data into tools without an explicit safe boundary.

When chaining tools/services:

- identify what information leaves ChatGPT/GitHub/local environment;
- prefer public-safe project artifacts for NotebookLM or similar external processing;
- do not include tokens, credentials, private correspondence, or confidential target-repository information;
- keep external-action authority separate from analysis/preparation.

## 11. Anti-ceremony rules

This program must not become a productivity hobby.

Do not:

- track token consumption as a success metric;
- schedule AI work solely to “use the plan”;
- create a new file for every background task;
- create a Skill before repeated value is demonstrated;
- build dashboards/queues/agents merely to manage a few prompts;
- run multiple redundant audit agents by default;
- convert every low-energy moment into mandatory work;
- create fake code/research/projects for background AI to process;
- keep outputs that Ali never uses;
- treat autonomous JobHunter/Sentinel progress as Ali learning time.

Prefer:

```text
real friction
→ smallest AI leverage experiment
→ actual use
→ evaluate attention ROI
→ only then persist/automate
```
