## 1. Question

This evidence set asks:

> Which current or very recent entry/transition responsibility bundles exist across relevant international and Iranian markets, what technical substrate and ownership do they actually require, and which hard access gates must be kept separate from technical fit?

The acquisition unit is **one distinct vacancy / responsibility bundle**, not one keyword hit and not one job title.

The normalization unit is:

```text
source + freshness
→ original title
→ geography / work mode
→ responsibility family
→ seniority / experience shape
→ technical substrate
→ verification / diagnosis responsibility
→ stakeholder / process responsibility
→ hard or unresolved access gates
→ evidence strength
```

## 2. Sampling and evidence rules

This is a targeted qualitative sample, not a probability sample of the global or Iranian labor market.

Rules:

- current employer/job-detail pages outrank aggregators;
- duplicate reposts count once;
- closed/recent vacancies may support responsibility-shape evidence but not current-opening claims;
- platform keyword-result counts are discovery evidence, not market prevalence;
- employer-explicit requirements remain separate from Career interpretation;
- education, language, nationality, residence and work authorization are access gates, not technical capability;
- absence from a JavaScript-only or crawler-restricted surface is not evidence that the vacancy family is absent.

### International conclusion

The strongest recurring accessible shape is not "junior programmer who manually writes everything." It is:

```text
technical substrate
+ integration / data-flow understanding
+ testing / troubleshooting / validation
+ AI-assisted execution
+ documentation / explanation
+ business or customer context
+ increasing bounded ownership
```

Current evidence also confirms that **early-career AI-assisted engineering is real**, including employers that explicitly value understanding, verification, troubleshooting and accountability over blank-page coding speed.

## 5. Normalized responsibility families supported by the combined sample

### Family A — Technical implementation / integration

Common work:

- connect systems through APIs/data feeds;
- inspect and validate JSON/XML/data structures;
- configure integrations;
- support onboarding/cutover;
- document behavior and workflows;
- troubleshoot integration failures;
- work with customer/business and engineering teams.

Evidence strength: **strong current international evidence; structurally plausible Iranian analogs through استقرار / پیاده‌سازی / ERP / software support surfaces.**

### Family B — AI automation / solutions / internal tools

Common work:

- map business process to an automation opportunity;
- use AI tools/agents/workflow platforms;
- write bounded Python/SQL/scripts or connect APIs;
- evaluate whether automation works;
- troubleshoot drift/failure;
- document and explain the solution;
- coordinate with stakeholders.

Evidence strength: **strong current international/UAE evidence; current Iranian AI surface exists but seniority varies widely.**

### Family C — Technical product / software support and diagnosis

Common work:

- logs and data-flow inspection;
- API/integration troubleshooting;
- SQL/data checks;
- reproduce and localize failures;
- communicate workaround/root cause;
- feed recurring defects back into product/engineering;
- maintain runbooks/knowledge.

Evidence strength: **strong current international and Iranian evidence.**

### Family D — QA / testing / evaluation

Common work:

- test behavior and acceptance criteria;
- reproduce failures;
- API/data validation;
- evidence/proof interpretation;
- defect reporting;
- sometimes automation/code/SQL.

Evidence strength: **strong current Iranian evidence and repeated international baseline evidence.**

### Family E — Applied AI engineering

Common work:

- Python/software substrate;
- LLM/RAG/agent integration;
- data preparation;
- evaluation/reliability;
- APIs/cloud/deployment to varying depths;
- debugging and product integration.

Evidence strength: **real junior/graduate routes exist, but many postings remain degree-, graduate-, experience- or production-depth gated.**

### Family F — Python application / backend / internal tools

Common work:

- Python application code;
- APIs;
- tests/debugging;
- data/SQL;
- packaging/configuration/reproducibility;
- team delivery.

Evidence strength: **large and real market family; current Ali-fit must be judged separately because implementation ownership requirements are commonly stronger.**

### Family G — Data / BI / analytics

Common work:

- SQL and relational reasoning;
- data quality;
- metrics/KPIs;
- reporting/dashboards;
- Python as supporting or core tool;
- stakeholder translation.

Evidence strength: **strong structural/current evidence; SQL is a common access/technical substrate.**

### Family H — systems / operations / SRE / technical infrastructure

Common work:

- Linux/network/system diagnosis;
- monitoring/logging;
- incident/operational reliability;
- scripting;
- infrastructure/cloud/deployment.

Evidence strength: **real adjacent route; often requires deeper operational substrate than Ali currently demonstrates.**

## 6. Cross-family recurring substrate

Across otherwise different families, the recurring core is:

```text
Python or equivalent technical scripting/application fluency
+ APIs / data structures / external systems
+ data / SQL at role-dependent depth
+ testing / validation / debugging / diagnosis
+ Git / collaborative engineering behavior
+ documentation / explanation
+ AI-tool fluency where relevant
+ process / customer / stakeholder understanding
```

No current evidence justifies replacing this substrate with prompt-only or tool-only training.

## 7. Access gates must remain separate

Current samples repeatedly contain hard or practical gates such as:

- university degree / graduate-program status;
- German or other local-language proficiency;
- nationality / residency / work authorization;
- UAE-national graduate programs;
- US-person / no-sponsorship restrictions;
- prior internship or one-to-three years of experience;
- location / on-site availability.

Career currently does not contain enough verified public-safe information to assume all of these are either satisfied or failed.

Therefore the vacancy decision model must be:

```text
responsibility fit
≠ current technical evidence fit
≠ access / eligibility fit
```

## 8. Market-evidence conclusion

The fresh sample strengthens four conclusions:

1. **The transition market is broader than junior developer / junior AI engineer titles.**
2. **Technical implementation/integration, product support/diagnosis, AI automation/solutions and QA/evaluation are legitimate engineering-adjacent entry/transition families.**
3. **AI-heavy early-career work still expects technical understanding, verification, debugging, data/API reasoning and accountable explanation.**
4. **Access gates are a first-class filter and can dominate otherwise strong responsibility fit.**

This evidence set does not by itself decide whether Ali is application-ready. That requires the formal E3 Career review against the Capability Ledger and public-safe profile.
