## 3. Rules for the entire period

### Rule A — Move at project-gate speed, not calendar speed

Do not artificially reserve one UpgradePilot step for one day.

If the current project gate passes in Block B, continue to the next project-authorized increment in Block C when energy and scope permit. If an entire bounded plan closes early, follow the next action selected by UpgradePilot `MEMORY.md`.

Career does **not** pre-authorize a later technical stage merely because this plan has remaining days.

### Rule B — Every active technical day contains one ownership action

An ownership action is not required to be a large implementation. Use the real work that already exists.

Examples:

- reconstruct a current responsibility from memory before reopening the explanation;
- predict what should change before AI implements it;
- predict expected test/output effects before running them;
- challenge a design, assumption, scope expansion, or AI debugging direction;
- make or direct a meaningful bounded modification;
- choose or materially alter a relevant test;
- state a failure hypothesis before asking AI to diagnose;
- explain what an observed result proves and what it does not prove;
- return to an earlier responsibility after several days and reconstruct it with reduced prompting.

Do not manufacture artificial exercises merely to satisfy this rule. UpgradePilot owns the technical method and may select the most useful project-local opportunity.

### Rule C — Learn inside UpgradePilot, not inside Career

Career may identify gaps and ownership targets. Technical teaching, source walkthroughs, implementation details, test design, and gap closure belong in UpgradePilot sessions with the AI working there.

### Rule D — Prediction before explanation when practical

Before a meaningful new implementation or debugging step, spend a short amount of time stating what you expect and why. Then compare your expectation with the AI/project result.

The goal is not to be correct every time. The goal is to make your own technical model visible enough to improve it.

### Rule E — Error first, hypothesis second, AI third

When a real failure occurs:

1. read the actual error/evidence;
2. state the likely layer/cause or at least two candidate causes;
3. then use AI to investigate and challenge the hypothesis.

Do not spend an arbitrary hour struggling alone. Even several focused minutes of independent localization is useful evidence.

### Rule F — No hour chasing

Do not extend a productive day only because the stopwatch is below a preferred number.

Default evening Block C to **1–2 hours**. Extend toward 3 hours only when energy remains genuinely good and the work is still high-value. Stop earlier when concentration degrades.

### Rule G — No new technical distraction

During this period:

- no second flagship;
- no Sentinel or AegisLab reactivation;
- no detached security/ML/blockchain project;
- no broad AI-tool or framework chase;
- no standalone SQL curriculum unless a current project/Career decision explicitly admits it;
- no JobHunter source-learning obligation;
- no large Career documentation project.
