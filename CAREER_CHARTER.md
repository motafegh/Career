# Career Charter

**Owner:** Ali Rajabi  
**Status:** Approved and controlling Career charter  
**Activated:** 2026-07-27  
**Responsibility:** Durable mission, scope, truth doctrine, repository boundaries, and long-term success definition

## 1. Mission

The Career repository is Ali Rajabi's durable, public-safe career operating system.

Its mission is to:

> Maintain an honest model of Ali's professional state, direct projects and learning toward realistic technical employment, preserve capability and assistance evidence, govern the project portfolio and market transition, and support repeated career cycles without duplicating project operation.

Career must remain useful before, during, and after any individual project or 90-day cycle.

## 2. Professional direction

Ali's long-term ambition is to become a hybrid engineer combining strong practical capability across:

- Python software engineering;
- data engineering and analytical systems;
- machine learning and applied AI;
- secure and trustworthy engineering;
- selected backend, cloud, distributed, automation, and MLOps responsibilities when evidence and career value justify them.

The current working identity is narrower and evidence-aware:

> **AI-augmented Python/data/ML engineer developing secure engineering capability.**

A working identity guides the current cycle. It is not a permanent title or a claim of demonstrated mastery.

## 3. Career operating model

The Career system connects:

```text
current profile
→ career strategy
→ project and learning allocation
→ preserved capability evidence
→ portfolio claims
→ market calibration
→ applications and interviews
→ employment feedback
→ revised profile and strategy
```

Projects are major capability-building and portfolio vehicles, but Career is about Ali rather than any one repository.

## 4. Career responsibilities

Career owns:

- the current public-safe career profile;
- long-term direction and current working identity;
- target role families, geography, and work-mode preferences;
- current career-cycle outcomes and capacity commitments;
- project portfolio roles and flagship allocation;
- project admission, support, pause, closure, and retirement decisions;
- cross-project capability assessment;
- portfolio and professional claim boundaries;
- employability and market-transition strategy;
- formal and event-triggered career reviews;
- the sole live career-level state and next career action.

Career may inspect project repositories deeply when a career question requires it. It records only the resulting career-level conclusion.

## 5. Project-repository responsibilities

Each project repository owns its own:

- product mission and technical boundary;
- live project position and exact continuation;
- routes, milestones, bounded plans, and blockers;
- source, tests, specifications, ADRs, commands, and outputs;
- technical evidence, working memory, experiments, and deployments;
- ordinary learning and implementation decisions.

For UpgradePilot, current technical truth belongs in `motafegh/UpgradePilot`, especially its `MEMORY.md`, active source, tests, plans, specifications, ADRs, commands, outputs, and environment.

Career must not recreate a project tracker or technical continuation file.

## 6. Evidence and honesty doctrine

Career conclusions must distinguish:

- exposure from demonstrated capability;
- guided application from independent application;
- project progress from Ali capability;
- AI generation from Ali direction, verification, modification, diagnosis, and ownership;
- a portfolio artifact from a defensible professional claim;
- a production-oriented project from a production-ready system;
- current evidence from stale or non-transferable evidence.

Career must not infer capability from:

- documentation volume;
- repository size or architectural sophistication;
- technology names;
- successful command execution;
- immediate repetition of an explanation;
- AI-generated implementation;
- passing AI-generated tests;
- project completion alone.

Strong claims require specific responsibility, evidence, assistance, recency, confidence, and transfer limits.

## 7. Learning and project philosophy

Ali's preferred learning mode is mission-driven engineering under real uncertainty:

```text
real objective
→ visible attempt
→ real output or failure
→ blocking concept or decision
→ targeted learning
→ implementation, test, or diagnosis
→ changed system behavior
→ increasing ownership
```

Career should favor:

- meaningful missions with narrow, ownable product boundaries;
- real and imperfect inputs;
- early end-to-end behavior;
- learning around active responsibilities;
- production-oriented quality without premature infrastructure;
- explicit scope and stopping controls;
- reduced AI dependence over time.

Career should reject detached technology collecting and projects created mainly to display résumé keywords.

## 8. Portfolio doctrine

A project may be:

- **Primary** — the main current capability and portfolio vehicle;
- **Supporting** — bounded work addressing a specific career gap;
- **Experimental** — time-boxed investigation without a portfolio promise;
- **Historical evidence** — completed, paused, or superseded work retained for lessons and claims;
- **Retired** — no active role beyond Git history or a concise record.

Only Career assigns these roles. Technical repositories decide how their authorized work is executed.

One primary flagship is the default. A new major project requires a demonstrated career need that the current portfolio cannot address proportionately.

## 9. Employability doctrine

Career work must eventually connect to real employment requirements.

Role readiness is assessed through:

- representative job-description requirements;
- specific capability evidence;
- portfolio artifacts and explanations;
- assistance and ownership boundaries;
- practical setup, testing, debugging, and delivery ability;
- interview and application feedback when available.

Applications should not wait for imaginary completeness, but they should begin through an explicit readiness decision rather than optimism or fear.

## 10. Public and private boundary

This repository is public.

It may contain public-safe professional facts, generalized constraints, portfolio evidence, and career decisions. It must not contain medical details, medication information, private legal matters, financial details, credentials, addresses, private contacts, confidential applications, or unnecessary personal routines.

Sensitive context may inform private reasoning but may not be copied into the repository.

## 11. Long-term success

Career succeeds when it helps Ali:

- build demonstrable, transferable technical capability;
- understand what he can and cannot yet do;
- select and constrain projects intelligently;
- create defensible portfolio evidence;
- calibrate against real roles;
- enter and progress through technical employment;
- make evidence-based changes without repeatedly restarting from zero;
- preserve ambition without self-deception or uncontrolled scope.

A career cycle may end with success, partial success, a changed direction, or a rejected hypothesis. Honest evidence and a better next decision are required in every case.

## 12. Authority and change control

The normal Career authority order is:

1. safety, legality, privacy, credentials, cost, health, and platform constraints;
2. Ali's explicit current instruction;
3. this charter;
4. `governance/CAREER_OPERATING_CONTRACT.md`;
5. `strategy/CAREER_STRATEGY.md` and active portfolio policies;
6. `plans/CURRENT_CAREER_CYCLE.md`;
7. `CAREER_STATE.md` for current career position;
8. capability, portfolio, market, and review records within their responsibilities;
9. AI recommendations.

Change this charter only when the durable Career mission, repository boundary, truth doctrine, portfolio doctrine, employability doctrine, or long-term success definition changes.
