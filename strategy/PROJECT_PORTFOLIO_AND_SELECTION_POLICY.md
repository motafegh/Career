# Project Portfolio and Selection Policy

**Owner:** Ali Rajabi  
**Status:** Approved and controlling project-portfolio policy  
**Activated:** 2026-07-27  
**Responsibility:** Project roles, admission, allocation, scope, reuse, review, closure, retirement, and portfolio claims

## 1. Purpose

Projects are major vehicles for capability, evidence, curiosity, and portfolio value. They are not the Career system itself.

This policy ensures that each project has a clear career role and that new work is admitted because it solves a real capability, portfolio, or market problem—not because a technology is interesting or a current project becomes difficult.

## 2. Project roles

Every project must have one Career role.

### Primary

The main current capability-building and portfolio vehicle.

Requirements:

- one meaningful mission;
- a bounded product or investigation scope;
- real or representative evidence;
- sufficient runway for current capability priorities;
- explicit ownership growth;
- protected allocation.

Only one primary project is active by default.

### Supporting

A bounded project or exercise addressing a specific gap not proportionately covered by the primary project.

Requirements:

- one named capability, portfolio, or market gap;
- narrow scope and time ceiling;
- no competing flagship identity;
- explicit completion or stop condition;
- evidence that the primary project cannot address the gap efficiently enough.

### Experimental

A time-boxed exploration whose outcome may be rejection or deferral.

Requirements:

- a question or hypothesis;
- a simpler comparison where relevant;
- fixed scope and cost ceiling;
- observable evidence;
- a decision: admit, support, defer, reject, or retire.

An experiment is not a project commitment or portfolio promise.

### Historical evidence

A completed, paused, superseded, or abandoned project retained for lessons and bounded claims.

Historical projects have no current tasks or continuation unless a new role is explicitly assigned.

### Retired

A project with no active Career role beyond Git history or a concise record.

Retirement is not failure. It may reflect completed value, poor fit, duplication, infeasibility, or an evidence-based decision to stop.

## 4. Admission decision order

A project proposal must be evaluated in this order:

```text
career problem or opportunity
→ target capability, portfolio, or market outcome
→ evidence that the need exists
→ whether an existing project can address it
→ smallest suitable project role
→ real user or stakeholder where applicable
→ meaningful output or decision
→ real or representative input
→ early end-to-end attempt
→ evaluation and evidence
→ scope, ownership, cost, and stop conditions
→ admission decision
```

Do not begin with a preferred technology and invent the mission afterward.

## 5. New-project admission gates

A new primary or supporting project must pass all applicable gates.

### Career-need gate

State:

- which target role or capability requires the work;
- which portfolio gap it fills;
- why the need matters now;
- what evidence supports the need.

### Non-duplication gate

Explain why:

- the primary project cannot cover the gap proportionately;
- a smaller exercise, contribution, or project increment is insufficient;
- existing historical work cannot be reused safely.

### Mission gate

For a product project, identify:

- one primary user or stakeholder;
- one central problem;
- one supported action, decision, or outcome;
- one main input family;
- one main output family;
- a meaningful technical or product thesis.

A project whose only user is “Ali learning technologies” is insufficient for primary flagship status.

### Early-flow gate

A credible end-to-end attempt must be possible early:

```text
real input
→ bounded processing or implementation
→ visible output or behavior
→ evidence and next question
```

Do not require weeks of infrastructure before the first complete attempt.

### Ownership gate

Define:

- which responsibilities Ali must understand, modify, test, diagnose, and explain;
- where AI generation is acceptable;
- how assistance decreases or ownership evidence increases;
- which prior work cannot be treated as proof.

### Scope gate

Define:

- included and excluded behavior;
- the initial product or exercise boundary;
- time/capacity ceiling;
- stop conditions;
- expansion triggers;
- closure evidence.

### Safety and feasibility gate

Reject or redesign work depending on:

- unauthorized access;
- private data without permission;
- unsafe execution;
- unsupported high-stakes claims;
- unaffordable infrastructure;
- unavailable credentials or data;
- legal or license conflicts;
- a dependency that makes the central mission infeasible.

### Portfolio gate

State the defensible future artifact and claim. A project should not be admitted solely because its technology list appears attractive.

## 6. Primary-project selection criteria

A primary flagship should normally provide:

- a stable mission capable of sustaining curiosity;
- a narrow, ownable product boundary;
- real and imperfect inputs;
- visible progress through the same end-to-end flow;
- production-oriented engineering responsibilities;
- important employment-critical capability;
- room for evaluation and honest negative results;
- sufficient portfolio differentiation;
- architecture that can grow from observed needs;
- a plausible path to increasing Ali ownership.

A primary project should be rejected or narrowed when it requires many unfamiliar ecosystems before producing value or when AI-generated architecture is likely to outrun ownership.

## 7. Simultaneous-work limits

Default maximum:

- one primary project;
- zero or one supporting project;
- at most one bounded experiment at a time.

A supporting project and experiment should not both be active when they reduce primary-project ownership or career-cycle outcomes materially.

Small exercises inside a project or learning session do not automatically count as separate projects.

## 8. Technology admission inside projects

Career does not select ordinary project dependencies or architecture.

At Career level, a technology is justified only when it supports:

- a real project responsibility;
- a target-role capability gap;
- a bounded experiment;
- a portfolio claim that cannot be demonstrated more simply.

Curiosity may justify a proposal or short experiment. It does not justify permanent architecture or a new repository automatically.

## 9. Historical-project reuse

Before reusing Sentinel, AegisLab, or another historical project:

1. name the current career question;
2. identify the exact evidence or component needed;
3. inspect current relevance and quality;
4. disclose original AI assistance and limitations;
5. avoid inheriting architecture or dependencies automatically;
6. prefer a bounded extraction, explanation, or comparison over project reactivation;
7. record whether the reused item supports capability, portfolio, or only historical context.

Historical project size is not a reason to reactivate it.

## 10. Project review

Career reviews a project's role when:

- a major gate changes its career contribution;
- planned capability evidence is not appearing;
- ownership is not increasing;
- workload or motivation is repeatedly unsustainable;
- market evidence changes portfolio priorities;
- scope expansion threatens the current cycle;
- the project reaches a meaningful closure point;
- Ali requests review.

Review outcomes:

- continue unchanged;
- narrow;
- change supporting allocation;
- reclassify;
- pause;
- close successfully;
- retire;
- replace as primary through a formal selection decision.

Career records the role decision, not technical continuation.

## 11. Project closure

A project closure record should state:

- original career role;
- actual outputs;
- demonstrated capabilities and assistance;
- portfolio artifacts;
- rejected or unfinished approaches;
- known limitations;
- current project status;
- what is preserved;
- whether future reactivation has a valid trigger.

A product need not achieve every target to produce valuable evidence. Unsupported claims must be removed.

## 12. Portfolio claim standard

For each project, Career should preserve:

- problem and user;
- Ali's actual role;
- implemented or investigated scope;
- strongest evidence;
- AI assistance;
- what Ali can explain, modify, test, or diagnose;
- limitations and non-claims;
- relevance to target roles;
- links to public evidence.

Do not describe a project as fully “built by Ali” when substantive architecture, code, testing, or reasoning was AI-generated without corresponding ownership evidence.

## 13. Project-record maintenance

`portfolio/PROJECT_PORTFOLIO.md` owns the current project list and roles.

Individual project records own stable career significance and claim boundaries. They must not record technical next actions.

Project repositories remain canonical for implementation details.

## 14. Change control

Change this policy only when project role definitions, admission gates, simultaneous-work limits, reuse rules, review/closure logic, or portfolio claim standards change.

A new project does not require changing the policy unless it exposes a missing general rule.
